# Adding a Language: Developer Runbook

> **Canonical runbook for adding a new locale to Breeze.** End-to-end,
> frontend + backend. Keep this in sync with the actual file paths, since it
> is the source of truth for the operation.
> Related: [translator-guide.md](./translator-guide.md) ·
> [architecture.md](./ARCHITECTURE.md)

This walks through adding **Spanish (`es`)** as a concrete example. Substitute
your locale tag throughout. Before starting, confirm the tag follows the
locale-naming convention: neutral language subtag (`es`, `fr`, `de`) unless a
regional variant is genuinely needed (`pt-BR`, `zh-Hans`).

---

## Prerequisites

- The i18n infrastructure is in place: `@lit/localize` configured, the
  `internal/i18n/` package exists.
- `@lit/localize-tools` is installed as a UI dev dependency (used by the
  `make i18n-extract` / `i18n-build` targets).
- You're on a clean git branch.

---

## Step 1: Verify the locale tag and plural rules

1. Confirm the BCP 47 tag is correct at
   https://www.iana.org/assignments/language-subtag-registry (or just trust
   CLDR).
2. Look up the locale's **CLDR plural rules** at
   https://unicode.org/cldr/charts/latest/supplemental/language_plural_rules.html.
   This tells you which plural categories (`one`/`other`/`few`/`many`/`two`)
   the language uses. You'll need this for the frontend XLIFF keys and the
   go-i18n TOML plurals.
   - English/French use `one` + `other`. Arabic uses
     `zero`/`one`/`two`/`few`/`many`/`other`. Russian uses
     `one`/`few`/`many`/`other`.
3. Note the `one` boundary especially. French treats `{0,1}` as `one`, while
   English treats only `{1}` as `one`. If the boundary differs from English,
   add a plural-boundary regression test (see Step 8).

## Step 2: Frontend: register the locale in `@lit/localize`

Edit `ui/lit-localize.json` to add the new code to `targetLocales`:

```jsonc
{
  "sourceLocale": "en",
  "targetLocales": ["fr", "es"],   // ← add "es"
  "inputFiles": ["src/**/*.ts"],
  "output": {
    "mode": "runtime",
    "outputDir": "src/i18n/locales",
    "localeCodesModule": "src/i18n/locale-codes.ts"
  },
  "interchange": {
    "format": "xliff",
    "xliffDir": "src/i18n/messages"
  }
}
```

Then regenerate the locale-codes module and extract the new locale's XLIFF:

```bash
# From repo root (uses the Makefile target; see Step 9)
make i18n-extract
# equivalent to:
#   cd ui && deno run npm:@lit/localize-tools@0.12.2 extract --config=lit-localize.json
```

This creates `ui/src/i18n/messages/es.xlf` (source strings only, `<target>`
empty) and updates `ui/src/i18n/locale-codes.ts` to include `es` in
`targetLocales`/`allLocales`.

## Step 3: Frontend: translate the XLIFF

Hand `ui/src/i18n/messages/es.xlf` to a translator (or follow
[translator-guide.md](./translator-guide.md) to edit it yourself). The
translator fills in every `<target>` element. Do **not** edit `<source>`
elements; those are regenerated from `msg()` calls in code.

```xml
<trans-unit id="s1234567890abcdef">
  <source>Save changes</source>
  <target>Guardar cambios</target>     <!-- translator fills this -->
</trans-unit>
```

For plurals (separate-key pattern), each plural category is its own
`<trans-unit>`. Dynamic values appear as `<x>` placeholder markers (generated
by `lit-localize` from `${…}` in the `msg(str\`…\`)` call); preserve them
verbatim in `<target>`:

```xml
<trans-unit id="comments_one">
  <source>{count} comment</source>
  <target>{count} comentario</target>
</trans-unit>
<trans-unit id="comments_other">
  <source>{count} comments</source>
  <target>{count} comentarios</target>
</trans-unit>
```

> Note: the literal `{count}` above is shorthand. In real `.xlf` files,
> interpolated values are emitted as `<x equiv-text="count"/>` placeholder
> elements (see [translator-guide.md](./translator-guide.md)). Translators move
> these markers into the right position in `<target>` but never edit or remove
> them.

## Step 4: Frontend: build the runtime locale module

```bash
make i18n-build
# equivalent to:
#   cd ui && deno run npm:@lit/localize-tools@0.12.2 build --config=lit-localize.json
```

This generates `ui/src/i18n/locales/es.js` (lazy-loaded at runtime when a user
selects `es`). **Commit this generated file**; it is needed for reproducible
builds. The generated locale `.js` files ARE committed, unlike `ui/src/api/`
which is regenerated by `make api-types`.

## Step 5: Frontend: add the locale to the Settings dropdown

Edit `ui/src/features/settings/user-settings-page.ts`, the `LANGUAGES` array:

```typescript
const LANGUAGES = [
  { value: "en", label: "English" },
  { value: "fr", label: "Français" },
  { value: "es", label: "Español" },   // ← add
];
```

No other frontend change is needed. `setLocale()` (in `ui/src/i18n/index.ts`)
discovers locales from the generated `locale-codes.ts`, and the locale loader
lazy-imports `./locales/${locale}.js`.

## Step 6: Backend: add the locale's TOML catalogs

For each message domain, copy the English file and translate:

```bash
# Mail
cp internal/i18n/messages/mail/active.en.toml internal/i18n/messages/mail/active.es.toml
# Push
cp internal/i18n/messages/push/active.en.toml internal/i18n/messages/push/active.es.toml
# Errors
cp internal/i18n/messages/errors/active.en.toml internal/i18n/messages/errors/active.es.toml
```

Edit each `active.es.toml` to translate the `other` (and plural category)
values. The go-i18n TOML format uses `text/template` placeholders
(`{{.Name}}`) matched by `TemplateData` map keys:

```toml
# internal/i18n/messages/mail/active.es.toml
[MentionSubject]
other = "Fuiste mencionado en {{.Org}}"

[MentionBody]
one = "{{.Actor}} te mencionó en {{.Org}}"
other = "{{.Actor}} te mencionó en {{.Org}}"

[PasswordResetSubject]
other = "Restablece tu contraseña de Breeze"
```

Named variables use `text/template` syntax. `{{.Name}}` in the message is
filled from `TemplateData: map[string]any{"Name": …}` in the `LocalizeConfig`
(see the [go-i18n docs](https://pkg.go.dev/github.com/nicksnyder/go-i18n/v2/i18n)).
Plural categories are `one`, `other`, and (if the language needs them)
`few`/`many`/`two` per Step 1's CLDR lookup. The backend caller passes
`PluralCount` to select the right category.

## Step 7: Backend: register the locale

Edit `internal/i18n/locale.go` to add the new tag to the supported-locales
list:

```go
var supportedLocales = []string{
    SourceLocale, // "en" (default, source)
    "fr",
    "es", // ← add
}
```

The bundle loader (`internal/i18n/i18n.go`) picks up the new catalogs
automatically. It embeds everything under `messages/`:

```go
//go:embed messages/*/active.*.toml
var messageFS embed.FS
```

No per-file registration is needed. Keep `supportedLocales` in sync with
`ui/lit-localize.json`'s `sourceLocale` + `targetLocales`.

## Step 8: Add tests

1. **Frontend:** add the new locale to the locale-switching test (assert
   `setLocale("es")` re-renders a `@localized` component). If the locale's
   plural boundary differs from English (Step 1), add a plural-boundary
   assertion.
2. **Backend:** add `es` to the localized email/push/error rendering tests.
   Assert each message renders correct Spanish text, and that a missing
   message ID falls back to `en`.
3. **`ResolveLocale()`:** add a case asserting `es` is matched and unknown
   tags fall back to `en`.

```bash
go test ./internal/i18n/... -run Locale
go test ./internal/service/... -run Localiz
```

## Step 9: Build and verify

```bash
# Regenerate frontend locale module + rebuild
make i18n-extract && make i18n-build
make build-ui          # tsc + vite build
deno check             # type-check (do NOT format src/i18n/locales/ or src/api/)

# Backend
make build             # go build (embeds the new TOML files)
go test ./...

# Lint
make lint-ui
```

**Do not run `make dev`** (AGENTS.md rule 12). For runtime/visual
confirmation, ask the user.

## Step 10: Commit and document

Commit with a message like:

```
feat(i18n): add Spanish (es) locale

- frontend: register es in lit-localize.json, translate es.xlf, build es.js
- backend: add active.es.toml for mail/push/errors, register in locale.go
- settings: add Español to language dropdown
- tests: locale switching, plural boundary, fallback
```

Note the locale in the Settings `LANGUAGES` dropdown
(`ui/src/features/settings/user-settings-page.ts`) if it is a launch locale.

## Common pitfalls

- **Forgetting `make i18n-build`** after translating the XLIFF. The runtime
  `.js` won't update and the new translations won't appear.
- **Editing `<source>` in the XLIFF.** These are regenerated from `msg()`
  calls; edits get overwritten on the next `extract`.
- **Missing a plural category.** If CLDR says the language has `few`/`many`,
  the TOML must include those keys or `Localize` falls back to `other`
  (acceptable, but loses grammatical correctness).
- **Not committing `locales/<locale>.js`.** The lazy import fails at runtime
  if the file is gitignored.
- **Hardcoding the new locale somewhere** instead of going through
  `getLocale()`/`setLocale()`. That breaks runtime switching.
